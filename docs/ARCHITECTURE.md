# Architecture

A high-level map of how CardJoy fits together. For how to *build* something, see
[DEVELOPMENT.md](./DEVELOPMENT.md).

## Overview

CardJoy is a Rails GraphQL API with a React/TypeScript frontend.

```
            ┌─────────────────┐
            │  web (consumer) │                React + Vite + TypeScript
            │   :3001         │                Apollo Client, shadcn/ui
            └────────┬────────┘
                     │ GraphQL over HTTP
                     ▼
         ┌───────────────────────┐
         │   api (Rails, :3000)  │            Rails 8.1, API-only
         │   /graphql endpoint   │            graphql-ruby, Sorbet-typed
         │   GoodJob (in-process)│            JWT auth, Rack::Attack
         └───────────┬───────────┘
                     ▼
         ┌───────────────────────┐
         │      PostgreSQL       │            app data + GoodJob queue
         └───────────────────────┘
```

## Components

### `api/` — Rails backend
- **Rails 8.1, API-only.** Single GraphQL endpoint at `POST /graphql`
  (`app/controllers/graphql_controller.rb`), plus a `/up` health check.
- **GraphQL** (`graphql-ruby`) lives under `app/graphql/`:
  - `types/query_type.rb` — read fields (e.g. `styles`, `cardOccasions`).
  - `types/mutation_type.rb` — the registry of every mutation.
  - `mutations/*.rb` — one class per write operation.
  - `types/*_type.rb` — GraphQL object types, usually mapping to models.
- **Models** (`app/models/`) are ActiveRecord. Some domain values are plain Ruby constants rather
  than tables — e.g. card occasions are `Card::OCCASIONS`, not a DB table. Card **styles** *are* a
  table and are loaded by `db/seeds.rb`.
- **Auth** is token-based: clients send `Authorization: Bearer <JWT>`; the resolver reads
  `context[:current_user]`. Google Sign-In validates an ID token against `GOOGLE_CLIENT_ID`.
- **Background jobs** use **GoodJob** (Postgres-backed) running *in-process* inside Puma — there is
  no separate worker and no Redis required. See `config/initializers/good_job.rb`.
- **File storage** uses ActiveStorage. Uploaded images are served via their public storage URL
  (`config.x.cdn_host`).
- **Types**: the backend is checked with **Sorbet** (`srb tc`); RBIs are generated by **Tapioca**.
- **Metrics reporting timezone is UTC.** Every day-bucketed metric
  (`Queries::AdminMetrics`, `Queries::DailyMetrics`, and `MetricsWindowRange`'s window
  boundaries) groups on the UTC calendar day — `config.time_zone` is unset, so `Time.zone`
  and `Date.current` are both UTC, and `created_at` is stored as a UTC instant with no
  zone conversion applied by `GROUP BY DATE(created_at)`. See the comment atop
  `app/services/metrics_window_range.rb` for the full reasoning.
- **`pg_trgm` is deliberately not enabled (#185).** Admin search (`AdminListable#admin_search_scope`)
  matches `title` / `external_id` / owner `name` / `email` with a leading-wildcard `ILIKE`, which
  cannot use a plain btree index — only a trigram GIN index would help. Benchmarked against 200k
  synthetic cards, that search costs ~50ms as a parallel seq scan regardless of which btree indexes
  exist, while every production table today is a small fraction of that size, so the seq scan is
  effectively free. Revisit once `cards` (or another searched table) approaches the tens-of-thousands
  of rows where this stops being true — add the extension and GIN trigram indexes on
  `cards.title` / `invitations.title` / `users.name` / `organizations.name` at that point rather than
  paying the write-amplification cost now for a table too small to need it.

### `web/` — consumer app
- React + Vite + TypeScript. Routes are declared in `src/App.tsx`; pages live in `src/pages/`.
- Talks to the API through **Apollo Client** (`src/lib/apollo-client.ts`), which injects the JWT
  from `localStorage` on every request.
- UI is built with **shadcn/ui** components in `src/components/ui/`.
- Optional integrations (GIPHY, Unsplash, PostHog) are feature-gated on their `VITE_*` env keys —
  blank key = feature hidden, no crash.

### Admin dashboard — separate private repo
- The internal admin dashboard was extracted out of this repo. It's the same stack as `web`
  (React + Vite + Apollo) and talks to the same `/graphql` endpoint as a second client.
- The admin-scoped part of the schema stays here in `api/` — `types/admin_*`, `queries/admin_*`,
  and the admin mutations. They're authorization-checked like any other field, so removing them
  because "the admin app is gone" would break the dashboard.

## Registry (the fourth product)

A registry is a list of things someone wants, for an occasion, that friends and family can claim.
It grew out of an invitation's wish list, so the model and GraphQL names are still `WishList*`
(`upsertWishList`, `WishListType`); the product name is Registry.

- **Data.** `wish_lists` belong to a `user` and optionally to an `invitation`; with no invitation
  it is a *standalone* registry (`standalone?`) with an `occasion`, `event_date` and a public
  `external_id`. `wish_list_items` carry `quantity`, `position` and `priority` ("most wanted").
  A guest's claim is a `wish_list_reservations` row (`purchased_at`, `reminded_at`); the claim's
  `token` is the guest's only credential and is a bearer secret, so treat it like a
  password: it rides in emailed links (`?claim=`) and the guest's `localStorage`.
- **Who sees what.** `surprise_mode` hides who claimed what from everyone, owner included.
  Per-item `claimed` is public, so owner-only totals (`WishList#insights`) leak nothing new. The
  owner's *thank-you list* (`thankYouList`) stays locked in surprise mode until `event_date` has
  passed. A hidden (`visible: false`) registry reads as missing to everyone but its owner, in
  GraphQL and in the `/p/registry/:id` share preview alike.
- **Ship-to address.** Opt-in per registry (`share_address`, default off). The owner's profile
  address (`HasReturnAddress`) is returned only through `WishListClaimType#ship_to`, for a valid
  claim token while sharing is on, and each reveal is logged. It is never a field on `WishListType`.
- **Anonymous access.** Guests have no account. `GraphqlController::PUBLIC_OPERATIONS` is an
  allow-list of *operation names*, so a new guest-facing query must be named to match
  (`GetRegistry`, `GetWishListClaim`, `ReserveWishListItem`, ...). Anything else returns 401.
- **Jobs** (GoodJob cron, `config/initializers/good_job.rb`): `OccasionReminderJob` (14:00 UTC),
  `RegistryEventReminderJob` (14:30, owners, once within 14 days of the event, per-registry
  opt-out) and `StaleWishListClaimsJob` (15:00, remind unbought claims after 14 days, release 7
  days later; purchases are never touched) and `ScrubGuestEmailsJob` (15:30, see below). All are
  idempotent via a timestamp column or by matching nothing once done.
- **Archive and retention.** Once `event_date` has passed a registry is archived
  (`WishList#archived?`, derived, never stored): readable, but `reserveWishListItem` refuses new
  claims and the stale-claim job leaves its claims alone. Guest emails are erased
  `WishList::GUEST_EMAIL_RETENTION` (7 days) after the event; the claim and guest name stay for
  thank-you notes, so `guest_email` is nullable and only required on create. A registry with no
  date never archives and keeps its emails. A new date (the yearly reset) un-archives it.
- **Passcode.** An owner may protect a registry (`wish_lists.passcode_digest`, salted PBKDF2, write-only).
  `registry(externalId, passcode)` errors `PASSCODE_REQUIRED`/`PASSCODE_INVALID`; `reserveWishListItem`
  takes the passcode too, because item ids are sequential. The `/p/registry/:id` unfurl turns generic,
  and `passcode` requests are throttled (`config/initializers/rack_attack.rb`). Keep any new
  guest-facing read behind `WishList#open_to?`.
- **Smaller pieces.** Items carry `price_updated_at` (guests see "price may have changed" after 30
  days; `RefreshWishListPricesJob` re-reads prices daily in bounded batches, never on a page view) and a free-text `section` (the guest page groups by it). `WishListType#qrSvg` is owner-only
  and drawn per request with `rqrcode`. The cover image is an ActiveStorage attachment set by its own
  owner-only mutations (`setRegistryCoverImage` checks type and size *before* attaching); it appears on
  the guest page and the `/p/registry/:id` unfurl, except behind a passcode.
- **Occasion reminders.** The reminder email links the contact's registry (`Contact#registry`),
  matched by email to an account with a shared, unarchived standalone registry.
- **Cards and invitations link out.** `cards.wish_list_id` and `invitations.registry_id` point at one
  of the owner's registries; the card/invitation page (and the 1-on-1/viewer emails) link to it only
  while it is shared, and `RegistryLinkType` hides the title of a passcode-protected one.
- **Link previews.** `WishListLinkPreview` fetches OpenGraph and schema.org JSON-LD for a pasted
  URL. It treats every URL as attacker-controlled (public-IP check on every hop, the vetted IP is
  pinned for the connection, size/time/redirect caps); keep those properties when changing it.
- **Admin metrics.** `Queries::AdminMetrics` counts standalone registries, items, claims and
  purchases (aggregate only). The dashboard that charts them is in the private admin repo.

Money is deliberately out of scope: guests buy from the retailer, or send cash through the owner's
own payment app. CardJoy never holds funds (see `WishListContribution`).

When a change adds a column or field the web reads, deploy the API before the web.

## Request lifecycle (example)

1. The web app fires a GraphQL mutation via an Apollo `useMutation` hook.
2. Apollo attaches the JWT and POSTs to `/graphql`.
3. `MutationType` routes to the matching `Mutations::*` class; `resolve` reads `current_user`,
   does the work in a transaction, and returns `{ <payload>, errors }`.
4. The frontend reads the typed result and updates the UI.

## Environments & config

Local development runs entirely in Docker (`docker compose` / the `Makefile`). Configuration is read
from environment variables with a fallback to Rails encrypted credentials, so local dev works out of
the box. See `CLAUDE.md` for the config conventions.
